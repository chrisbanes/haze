    Benchmark results¶

    The latest available Android measurements for each comparison are collected here. Use the performance guide to choose what to try on your screen, and the benchmark runbook to reproduce Haze's workloads. Sections use different devices and builds: compare configurations within a table, not timings across sections.

    Reading the results¶

    • CPU frame duration measures UI-thread and RenderThread cost, not GPU shader duration.
    • Frame overrun measures how far a frame finishes past its deadline. Negative values mean spare time; more negative is better.
    • P90 describes the slower end of the measured frames. Negative P90 overrun does not mean every frame met its deadline.

    These are measurements of specific sample workloads, not performance budgets for other apps. Each section records its aggregation method and measurement conditions.

    Performance modes¶

    These are the latest source-backed results for Quality, Balanced, and Performance with stable and continuously changing source input. They used a Pixel 8a running Android 17 (full SDK 37.2) at 60 Hz, with fixed-performance mode enabled and normal Android CPU scheduling.

    Values are P90 CPU frame duration / P90 frame overrun, in milliseconds, as reported by AndroidX for one pass of eight measured iterations per method. These are single-pass values, not averages across passes. Other style choices stay fixed within each sample.

CPU frame duration also does not measure GPU shader cost. Repeat with reversed run order and check appearance on your screen before choosing an override.

    The measured code and regenerated 3,043-rule baseline profile match commit 68439df3. Both target and benchmark used benchmarkRelease; the target APK was minified. The table's complete pass produced 96 measured iterations and 96 Perfetto traces. JSON method identity, XML success, eight metric runs, and eight distinct non-empty trace references were verified for every method. Slower completed iterations were retained.

Two selected methods received normal-scheduling repeats; changing-input Balanced Glass also received two passes restricted to the middle CPU cluster, with main-thread and RenderThread placement verified in all 16 current-build traces. Those controlled results are excluded from these tables.

    An incomplete attempt with a Google-app Chromium trace-producer delay was preserved separately and excluded. The Google app was temporarily disabled for accepted measurements.     Backdrop versus Sources¶

    Native Android Backdrop reads pixels behind the effect from the window, instead of using captured hazeSource content. See Backdrop guidance for its practical benefits, fallback requirements, and experimental feature flag.

    This comparison used Quality on a Pixel 8a running Android 17 (full SDK 37.2) at 60 Hz, with fixed-performance mode enabled and normal CPU scheduling. Each method ran eight iterations in each of two passes, reversing both method and workload order.

    Values are the arithmetic mean of the two per-pass P90s, not the P90 of pooled frames.

    Quality workload Sources CPU P90 (ms) Backdrop CPU P90 (ms) Backdrop CPU difference Sources overrun P90 (ms) Backdrop overrun P90 (ms)
    Blur, stable input 4.59 5.07 10% higher -7.75 -2.44
    Blur, changing input 4.59 5.12 12% higher -5.40 -2.21
    Glass, stable input 3.54 5.18 46% higher -10.69 -0.48
    Glass, changing input 3.46 4.24 23% higher -1.84 -0.48
    Nine Glass nodes, changing input 3.94 4.74 20% higher -6.85 -5.18

    Backdrop had higher CPU P90 in both passes for changing-input Blur and all Glass workloads. All rows retained negative P90 overrun, but Backdrop left less deadline margin. Stable Blur's ranking reversed between passes, so its average does not establish a consistent difference.

    Stable input is not an idle screen

    These workloads continuously invalidate the effect while leaving source pixels unchanged. They compare retained source output with repeated native Backdrop composition. Use the changing-input rows as the closer reference for scrolling or animated content. These results do not establish that Backdrop is slower on every screen.

    Measurement details

    The benchmarkRelease build used commit f06cd64a; the Android build was CP41.260814.003.B1. The device was on AC power at 100% charge. The first pass started at thermal status 0 and battery temperature 26.0°C; after cooling, the reverse pass started at thermal status 0 and 28.1°C. Brightness was unchanged and not recorded.

    Ten methods, eight iterations each, and two passes produced 160 measured iterations and 160 Perfetto traces. The first pass ran Sources then Backdrop for each workload. One interrupted second-pass attempt was replaced; no completed comparison was discarded. The Google app was force-stopped to prevent its Chromium trace producer from adding a known collection delay. Table values and percentage differences were calculated before rounding.

    Native Backdrop trace counters were present with zero source records, confirming that the native rows did not measure source fallback. Backdrop also used less peak GPU memory: the recorded difference was approximately 6–10 MB, based on the mean of each pass's median memoryGpuMaxKb value.

    Perfetto showed scheduler variation: the mean per-iteration RenderThread time share on the little CPU cluster ranged from 0.9% to 49.6% across method executions. Stable Glass remained slower with comparable placement in the first pass and more favourable Backdrop placement in the reverse pass. This supports a narrower conclusion: native Backdrop was not a CPU performance win for this Glass scene on this device.

    Raw JSON, benchmark messages, and traces are retained locally under internal/benchmark/build/pixel8a-2026-09-12-full-backdrop-2pass/.

    Glass fixed quality¶

    This comparison isolates six qualityFraction settings for one 280 dp × 180 dp Regular Glass surface using HazeInput.Sources. It used a Pixel 6 running Android 17 (full SDK 37.1) at 60 Hz, with fixed-performance mode enabled.

    Controlled CPU placement

    The sample's main thread and RenderThread were restricted to the middle CPU cluster. These are controlled quality comparisons, not expected timings under normal Android scheduling. Do not combine them with the Pixel 8a mode results above.

    The table shows changing-input results. Each value is the arithmetic mean of two per-pass P90s, calculated before rounding, not the P90 of pooled frames.

    qualityFraction CPU frame duration: mean per-pass P90 (ms) Frame overrun: mean per-pass P90 (ms)
    0 3.17 -10.95
    0.25 3.12 -10.17
    1f / 3f 3.11 -9.77
    0.5 (Balanced) 3.17 -9.11
    0.75 4.87 -6.34
    1 (Quality) 4.74 -5.53

    For this scene, Fixed(0.75f) left 2.77 ms less deadline margin than Balanced. No measured frame missed its deadline. These results do not establish the right setting for Web, Clear Glass, larger or multiple surfaces, or higher refresh rates. Check both appearance and frame timing on the actual screen under normal scheduling.

    Measurement details

    The sweep used a release build. The sample process requested affinity to CPUs 4–5; every Perfetto trace confirmed that main and RenderThread executed only on those CPUs during measurement. Other Android processes remained unrestricted.

    Six levels ran with stable and changing input, first in ascending quality order, then descending with workload order reversed. Eight iterations per case produced 192 iterations and 34,753 measured frames. No completed timing iteration was discarded. Runs started at thermal status 0 and a battery temperature at most 30°C. Brightness was fixed during measurement; cooldowns dimmed the screen and disabled fixed-performance mode.

    The largest changing-input CPU P90 difference between passes was 0.12 ms. Stable-input CPU P90 ranged from 2.60 to 2.72 ms across all levels and both passes.

    An earlier normal-scheduling experiment showed CPU rankings sensitive to slower-core placement, including a reversed ranking when two levels were repeated. That experiment remains in git history. This controlled sweep also fixed brightness, so differences between the experiments cannot be attributed to CPU affinity alone.

    Glass containers¶

    This comparison draws two Regular Glass surfaces, each about 134 × 180 dp and 12 dp apart, over a continuously changing source. The independent row draws them separately. The container row wraps the same surfaces in hazeGlassContainer(spacing = 32.dp), so they merge into one cluster. Both rows use HazePerformanceMode.Default and HazeInput.Sources. It used a Pixel 8a running Android 17 (full SDK 37.2) at 60 Hz, with fixed-performance mode enabled and normal CPU scheduling.

    Each per-pass value pools the frames of that pass's eight iterations; the table shows the arithmetic mean of the two per-pass values. Peak GPU memory uses each pass's median memoryGpuMaxKb.

    Row CPU frame duration P50 (ms) CPU frame duration P90 (ms) Frame overrun P90 (ms) Peak GPU memory (KB)
    Independent surfaces 2.97 4.86 -7.26 100,016
    One container cluster 2.84 4.51 -2.79 107,190

    Both rows re-rendered their Glass layers on every frame. HWUI's drawLayer [graphicsLayer] slice shows what each row drew:

    Row graphicsLayerDrawCount per frame Layer size (px)
    Independent surfaces 1.93–2.00 two 527 × 623 layers
    One container cluster 0.95–1.00 one 952 × 745 layer

    The cluster draws one layer that covers both members and the bridge between them. The cluster's single layer is about 8% larger in area than the two independent layers combined.

    The container row had 0.35 ms lower CPU P90, but about 4.5 ms less deadline margin at P90 and 7,174 KB (about 7%) more peak GPU memory. CPU frame duration does not measure GPU shader cost. These runs did not measure GPU timings, so they do not show why the container finished closer to its deadline despite its lower CPU frame duration. Neither row missed its deadline at P90.

    These results describe two surfaces at one spacing on one device. They do not establish the cost of larger clusters, more members, other styles, or higher refresh rates. Measure clustered screens against independent surfaces before adopting a container.

    Measurement details

    The benchmarkRelease APKs were built from commit 33e2371a. The sample APK SHA-256 was 0dab212a8b5d285b99ab9c1483352f43666b27a1242e0831ce66dbbe90a18194 and the benchmark APK SHA-256 was 5a9ea749589d95107cf2bf72d7671cc5825afe888ad57ebee4a257cbbf0c0c0a. The Android build was CP41.260831.007.A3. The device was on AC power at 80% charge, and both passes started at thermal status 0, with the battery at 27.8°C and 28.1°C.

    Each method ran eight measured iterations per pass in its own Gradle invocation. The first pass ran independent then container, and the second pass reversed that order. This produced 32 iterations, 32 Perfetto traces, and 5,846 measured frames. No completed iteration was discarded. Every iteration recorded one HazeSource.record per frame (0.95–1.00) and at least one HazeGlass.runtimeDraw, confirming the changing source and the runtime Glass path. The Google app was temporarily disabled to prevent its Chromium trace producer from delaying collection.

    The two passes agreed closely: per-pass CPU P90 differed by at most 0.08 ms, and frame overrun P90 by at most 0.12 ms.

    CPU placement differed between the rows. Main-thread placement was similar, with 72% (container) and 79% (independent) of its running time on the little cluster on average. RenderThread spent an average of 18% of its running time on the big core in the independent row, compared with 6% in the container row. Grouping iterations by RenderThread big-core share kept the same ranking. With at most 5% on the big core, the pooled CPU P90 was 4.80 ms independent (4 iterations) against 4.55 ms container (10 iterations). Above 5%, it was 4.90 ms (12 iterations) against 4.45 ms (6 iterations). The overrun P90 difference stayed between 4.2 and 4.7 ms in both groups.

    Raw JSON, benchmark messages, traces, per-iteration placement, and device readbacks are retained locally under internal/benchmark/build/benchmark-results/container.dy8ZmS/. The on-device sample check is recorded in the replan report.

    Lazy container scroll¶

    This comparison scrolls a five-column LazyVerticalGrid with 40–45 visible members inside hazeGlassContainer(spacing = 16.dp). Every member is its own cluster, so the workload isolates reclustering. Build A reclusters on every member notification. Build B coalesces them into one pass per frame (#1567). It used a Pixel 8a running Android 17 at 60 Hz, with fixed-performance mode enabled and normal CPU scheduling.

    Each per-pass value pools the frames of that pass's eight iterations; the table shows the arithmetic mean of the two per-pass values for each build.

    Build CPU frame duration P50 (ms) CPU frame duration P90 (ms) CPU frame duration P99 (ms) Frame overrun P50 (ms) Frame overrun P90 (ms) Measured frames, both passes
    A: recluster per notification 33.2 49.7 65.6 35.1 56.6 2,376
    B: one recluster per frame 27.7 32.5 35.7 18.6 24.5 2,830

    Build B cut main-thread running time inside the measured window from a mean of 3,005 ms to 1,412 ms, out of about 3,330 ms. In build A the main thread was busy for almost the whole window. RenderThread running time stayed similar, at 2,006 ms and 2,149 ms. Build B delivered about 19% more frames and roughly halved the overrun.

    Neither build met the 60 Hz deadline: 94% (A) and 97% (B) of frames overran. In build B neither thread was busy for the whole window: RenderThread ran for about 65% of it while drawing about 40 separate Glass layers. These runs did not measure GPU timings, so they don't show where the remaining frame time goes. The result describes this deliberately dense scene, not a typical container.

    The two-member container workloads above ran as guards in the same passes. The container row's mean CPU P90 was 4.82 ms (A) and 4.80 ms (B). The independent row's was 4.86 ms and 5.48 ms, but that difference came from one B pass at 6.31 ms; the other B pass, at 4.66 ms, was below both A passes. Neither guard missed its deadline at P90.

    Measurement details

    Build A was commit 7ffbcc45, which adds the scenario without a library change. Build B was commit 68217119, the head of #1592. The sample APK SHA-256 was b08454af9eb5bb363f8796339022994532ca0a00a45d0b8bdccf65e6edeb6c63 for A and b31b86e4e3951c999005cd969cfacd270ec333bd65ed7efe4c8ecee35a8a8b70 for B; both used benchmark APK 6dc136d3dacc31b813554622d8b2a518bad3748a63160d4f6822feb30172f93f. The Android build was CP41.260831.016. The device was on AC power at 80% charge and reported thermal status 0 before and after every pass. Battery temperature rose from 28.8°C to 33.9°C across the run.

    The passes ran in the order A, B, B, A, each running the lazy scroll and then both two-member guards, eight measured iterations per method in its own Gradle invocation. Each build was dry-run first. This produced 96 iterations and 96 Perfetto traces. The Google app was temporarily disabled to prevent its Chromium trace producer from delaying collection; an earlier pass that hit that delay was discarded and rerun.

    Build A slowed as the device warmed: its per-pass CPU P90 was 40.9 ms in the first pass and 58.6 ms in the last. Build B's per-pass CPU P90 was 32.6 ms and 32.5 ms. Using only the first, coolest A pass, build B still lowered CPU P90 by 8.3 ms and overrun P50 by 10.5 ms.

    CPU placement differed between builds. In every A iteration the main thread ran mostly on the big core and RenderThread mostly on the middle cluster. In every B iteration the scheduler swapped them. Build B's main-thread reduction was therefore measured on slower cores. Two of the 32 lazy-scroll traces, one per B pass, had no scheduler data in the measured window and are excluded from the running-time means. Build B's iterations split into two groups, with CPU P50 of 17.5–20.9 ms and 28.2–30.4 ms, without a matching placement difference.

    Raw JSON, benchmark messages, traces, per-pass device readbacks, and the discarded pass are retained locally under internal/benchmark/build/benchmark-results/lazy-container-2026-10-18/.

    Blur noise and tint shader reuse¶

    On Android 13 and newer, Blur combines nonzero noise with one SrcOver color tint in a single runtime shader. Animating radius, tint, or noise creates a new effect for almost every frame. This comparison measured constructing that shader for each new effect, then compiling it once per process and reusing it for every effect.

    It used a Pixel 8a running Android 17 (full SDK 37.2) at 60 Hz, with fixed-performance mode enabled and normal CPU scheduling. Each workload animates one property for three seconds over a constant 240 × 180 dp source-backed area, split across one or three nodes.

    Values are the arithmetic mean of two per-pass P90s, not the P90 of pooled frames. Constructions and their elapsed time are per three-second measured window.

    Workload Constructions before → after Construction time before (ms) CPU P90 before → after (ms) Overrun P90 before → after (ms)
    Tint, 1 node 127 → 0 51.1 5.11 → 5.29 -7.46 → -7.70
    Tint, 3 nodes 381 → 0 99.4 5.71 → 4.75 -6.22 → -7.07
    Radius, 1 node 180 → 0 70.1 5.53 → 5.01 -7.78 → -8.31
    Radius, 3 nodes 540 → 0 134.2 6.61 → 5.75 -7.03 → -7.77
    Noise, 1 node 180 → 0 77.6 6.66 → 6.26 -6.56 → -7.00
    Noise, 3 nodes 540 → 0 132.5 5.97 → 5.38 -6.01 → -6.30

    Reuse removed every warm construction. Before, each new effect constructed the shader on the main thread, taking roughly 0.25–0.45 ms each. A fresh process still constructs it once on first use. Stable styles constructed nothing in either build.

    CPU frame-duration changes are inconclusive. The two passes of one build differed by up to 1.47 ms in CPU P90, more than any before/after difference in the table. Three-node rows also ran with different CPU placement in each build, in both run orders, so their P90 differences cannot be attributed to shader reuse alone. Neither build missed its deadline at P90 in these workloads.

    Measurement details

    The benchmarkRelease builds used commits 0f81d5f4 (before) and 92168671 (after) with an identical benchmark APK; the Android build was CP41.260831.007.A3. The device was on AC power at 90% charge. Every method started at thermal status 0, with the big CPU at most 34°C and the battery at most 28.5°C. Brightness was unchanged and not recorded.

    Ten methods (the six rows above, stable one- and three-node controls, and one- and three-node process-cold launches) ran eight measured iterations in four passes: before then after, then after then before with method order reversed. This produced 320 iterations and 320 Perfetto traces. No completed iteration was discarded. The Google app was temporarily disabled to prevent its Chromium trace producer from delaying collection.

    Construction counts come from a HazeRuntimeShader.construct section nested in HazeBlur.combinedNoiseTint in the sample process. Its duration measures CPU-side construction, not backend or GPU shader compilation; GPU timings were not analyzed.

    Without reuse, three-node main-thread and RenderThread time ran about 97% on the middle CPU cluster. With reuse, more main-thread time ran on the little cluster and 22–30% of RenderThread time ran on the big core. Main-thread running time still fell by 58–90 ms per window for three nodes. Process-cold launches exceeded their deadline at P90 in both builds; their mean CPU P90 differed by less than 1 ms, passes differed by up to 3.49 ms, and the ranking varied between passes.

    Raw JSON, benchmark messages, traces, frozen APKs, and per-method device readbacks are retained locally under internal/benchmark/build/benchmark-results/noise-tint.eO1A65/.

    Placement update deduplication¶

    When an effect's size changed, Haze updated the effect twice in the same frame: once when Compose placed the node, and again when it reported the node's global position. The second callback now skips its update if the first already applied the same position, size, and transform, its source reads completed, and its sources haven't changed since (#1437). This comparison counts HazeEffectNode-updateEffect trace slices before and after that change in four Glass profiling workloads.

    It used a Pixel 8a running Android 17 (full SDK 37.2) at 60 Hz, with fixed-performance mode enabled and normal CPU scheduling. Each workload resizes one or nine Glass effects over a stationary source for three seconds; shapeUpdateBalanced also animates the corner radii with the size. See the controlled scenario baseline for the exact workloads. Each method ran eight iterations in each of two passes, in opposite build order.

    Values are before → after. Update counts pool both passes (16 iterations per build). Frame timings are the arithmetic mean of two per-pass P90s, not the P90 of pooled frames.

    Workload Effects updateEffect per effect per frame per animating frame CPU P90 (ms) Overrun P90 (ms)
    resizeQuality 1 1.90 → 0.96 1.99 → 1.00 5.35 → 5.40 -6.14 → -6.17
    resizeQuality9 9 1.84 → 0.93 1.99 → 1.00 12.72 → 12.53 0.58 → 0.62
    shapeUpdateBalanced 1 2.81 → 1.91 2.98 → 1.99 5.47 → 5.38 -6.83 → -7.06
    shapeUpdateBalanced9 9 2.76 → 1.85 2.99 → 1.99 12.94 → 12.75 0.47 → 0.24

    "Per frame" counts every main-thread frame in the measured window, including idle frames at its edges. "Per animating frame" counts only frames that ran at least one update.

    The change removed one update from each animating frame. The resize workloads went from two updates per effect to one. The shapeUpdateBalanced workloads went from about three to about two. In both builds, the remaining update in those workloads ran inside Recomposer:animation instead of during placement. That is consistent with the single update Glass runs when state read by its style changes, here the animated corner radius. A style-only frame already ran one update after #1434 and #1439, and this change does not merge that update with the placement update. The traces show where the update ran, not which code path requested it, so treat that attribution as likely rather than proven.

    The measurements show fewer updates, not a frame-time change. Build differences were at most 0.19 ms in CPU P90 and 0.23 ms in overrun P90, while the two passes of the same build differed by up to 0.42 ms and 0.50 ms. Both nine-effect workloads missed the frame deadline at P90 (positive overrun) in both builds. CPU frame duration does not measure GPU cost.

    Measurement details

    The benchmarkRelease builds used commits 903b02e9 (before) and 1f1c8a3a (after); the Android build was CP41.260831.007.A3. The commits differ only in HazeEffectNode and its tests. internal/benchmark and sample are identical, and both builds produced a byte-identical benchmark APK. The merged change also contains later commits that were not measured. One restructures the placement record and drops a per-placement array copy. The others make the skip rarer when sources join, leave, or change window during layout, and release references. These workloads keep their sources attached, stationary, and in one window, so the added conditions should not change their update counts, but the final code was not re-measured.

    The device was on AC power at 90% charge, and every readback reported thermal status 0. Before each measured run, all CPU sensors read 35°C or less and the battery 28.4°C or less; the runs waited until the CPU sensors read at most 33°C and the battery at most 28.5°C. The hottest CPU reading after a run was 48°C. The display stayed in its 60 Hz mode, and automatic brightness stayed enabled with the setting unchanged at 2. Fixed-performance mode pinned each CPU cluster to its maximum frequency during the passes. Force-stopping the Google app did not stop it from restarting immediately, so it was temporarily disabled to avoid its Chromium trace-producer delay. Fixed-performance mode was then turned off and the Google app was re-enabled.

    Four workloads, two builds, two passes, and eight iterations produced 128 measured iterations and 128 Perfetto traces. No completed iteration was discarded. Each method was dry-run on both builds and measured through its own selector. JSON method identity, XML success, iteration count, and trace count were verified before continuing. Pass 1 ran the before build and then the after build, in the order shown above. Pass 2 reversed both the build order and the method order.

An iteration counts as slow-core if either thread spent more than 25% of its running time in the window on the little cluster. Before the change, 2 of 16 resizeQuality and 2 of 16 shapeUpdateBalanced iterations were slow-core; after it, 4 and 3. No nine-effect iteration was. Excluding slow-core iterations, the pooled-frame CPU P90 moved from 5.23 to 5.20 ms for resizeQuality (14 and 12 iterations) and from 5.43 to 5.26 ms for shapeUpdateBalanced (14 and 13 iterations), which is also within the pass-to-pass variation. The table above includes slow-core iterations.

    Two passes per build is a small sample. Update counts were stable across iterations and passes (for example, 0.92–0.93 per effect per frame for resizeQuality9 after the change), but frame timings varied more between passes than between builds. Resolving a difference smaller than about 0.5 ms would need more passes, again in alternating order.

    Raw JSON, benchmark messages, XML, and traces are retained locally, outside the repository, under ~/dev/haze-worktrees/1437-artifacts/: before-903b02e9/ and after-1f1c8a3a/, each with pass1/ and pass2/. That directory also holds the dry-run XML, per-run device readbacks, the two builds' APK hashes, and the trace-analysis scripts.
